# 探索记录：从一个"打不开的菜单"到一个可用工具

这份记录按时间顺序写，每一步都给出当时看到的现象、证据，以及由此改变的结论。踩过的坑保留原样，因为正是这些坑决定了最后的结构。

验证环境：三星 Android 17（One UI）设备，SELinux Enforcing，未解锁 bootloader，未刷入任何持久化 root，KMI 分支 `android16-6.12`。

---

## 一、起点：普通应用打不开 ServiceMode

目标很窄：把一条 `keyString` 发给三星 ServiceMode 组件，让它打开工程菜单。

先确认能不能用普通 App 直接 `startActivity`。答案是不能：

```
java.lang.SecurityException: Permission Denial: starting Intent {
  cmp=com.sec.android.RilServiceModeApp/.ServiceModeApp ... }
  not exported from uid 1001
```

该 Activity 声明 `exported="false"`，并且跑在电话进程（uid 1001）里。`ActivityManagerService` 侧只有 uid 0 能跳过这个检查。

**结论：调用方必须是 root。**

顺带排除拨号暗码：`ServiceModeApp` 需要 `KEYTYPE` / `KEYSTRING` 的 `signature|privileged` 权限，拨号器不持有该签名权限，暗码路径构造不出可用的 Intent extras。

---

## 二、选择提权链：为什么是 DirtyFrag

手上有两条公开路线可选：

| | 需要 uid 2000（`pselect` / rt_mutex） | **DirtyFrag（CVE-2026-43284）** |
|---|---|---|
| 调用方权限 | 需要 shell | **普通 App 即可** |
| 原语 | 往内核栈伪造 `rt_mutex_waiter` | 篡改文件页缓存 |
| 匹配粒度 | 精确固件（指纹 + 内核 + SHA） | KMI 分支（`androidNN-X.Y`） |
| 本机结果 | 几何上不可能（反汇编确认缺口 0x90，fd_set 数组上限 2） | **一次成功** |

于是选 DirtyFrag。它在设备上做完的事，日志原文（去掉设备标识）：

```
[NewMethod] moteur DF (base 4.4.8 éprouvée, DirtyFrag CVE-2026-43284) — KernelSU
encap port: 53491
spi: 0x4f01b007
* ko android16-6.12 (6232 bytes)                ← KMI 自动匹配
* patch #1 (crash_dump64 ← splicehelper, 1312 bytes)
* patch #2 (libbinderdebug.so ← dirtyfrag.ko, 6240 bytes)
* /system/lib64/libc.so  hook=0x6e8b0 shell=0xf4c78
* /system/lib64/libc++.so hook=0xb4ae8 shell=0x10faa8
=== cleanup ===                                 ← 篡改全部还原
[NewMethod] DF rc=0
```

链路拆开看是六步：

```
① App 用公开 API 建 IpSec SA（openUdpEncapsulationSocket / allocateSecurityParameterIndex）
      → 得到一个能触发内核数据包处理的句柄
② 用页缓存漏洞替换「内存页」（不是磁盘）：
      /apex/.../crash_dump64          ← splicehelper
      /vendor/lib64/libbinderdebug.so ← 内核模块字节
      /system/lib64/libc.so + libc++.so ← shellcode 与 trampoline
③ 触发 usermode helper 以 root 加载被换掉的 libc
      → shellcode 在 u:r:vendor_modprobe:s0 里运行
④ shellcode 取出 .ko 并 insmod → dfr_lkm：关掉 SELinux enforce
⑤ ksud late-load → KernelSU 上线
⑥ cleanup：页缓存全部还原
```

关键点：**全程只改内存页缓存，不写任何分区**，所以保修位不动。硬重启后内核模块、Permissive 状态、`/system/bin/su` 全部消失。

## 三、第一个坑：root 有了，su 却用不了

DirtyFrag 报告成功后，界面显示已 root，但：

```
$ adb shell su -c id
/system/bin/sh: su: inaccessible or not found
```

于是去读上游实现，发现两处关键事实：

```kotlin
// 上游 App 里
n.setAllowShell(false)          // 默认关闭
```

```c
// 上游 wrapper 里
execl(KSU_LOGCAT_PATH, "logcat", "late-load", "--allow-shell", "--kmi", KSU_KMI, ...);
```

即 `allow_shell` 决定 **uid 2000 能不能用 root**，上游默认关掉。

接着试了"在管理器里授权"这条路，也走不通：

| 检查 | 结果 |
|---|---|
| 设备上已装管理器 | 版本 32601 |
| 捆绑 ksud 装载后的驱动 | 32659 |
| 管理器报错 | 版本过低，要求升级到 32659 或以上 |
| 上游与 Next 的所有发行版 | 最高都到不了 32659 |

没有匹配的管理器，授权 UI 用不了。又试"降级到官方 ksud"：下载与打补丁都成功，但重跑后 `DF rc=1`，官方二进制在本机内核上跑不通。

**最终方案：给 classic 加一层 wrapper**，让引擎执行的不是 ksud 本体，而是一个脚本：

```sh
#!/system/bin/sh
REAL=/data/data/<pkg>/ksud-real
[ -f "$REAL" ] || exit 1
/system/bin/cp -f "$REAL" /data/local/tmp/.ksud-stage || exit 1
/system/bin/chmod 755 /data/local/tmp/.ksud-stage || exit 1
/system/bin/mount -o bind /data/local/tmp/.ksud-stage /system/bin/atrace || exit 1
exec /system/bin/atrace late-load --allow-shell
```

逐行看为什么必须这样：

| 行 | 作用 | 为什么必须 |
|---|---|---|
| `cp` 到 tmp | 给 bind-mount 一个源 | 原地执行应用数据目录里的二进制会被拦 |
| `mount -o bind ... /system/bin/atrace` | 把 ksud 绑到系统路径 | 三星 DEFEX 只允许从系统路径的真实文件执行；`atrace` 是真实二进制，不是 toybox 符号链接 |
| `exec /system/bin/atrace late-load --allow-shell` | 执行 late-load 并放行 shell | 这一行才是拿到 shell root 的关键 |

### 这里踩的第二个坑

第一版 wrapper 写成直接 exec：

```sh
exec "$REAL" late-load --allow-shell      # 错
```

现象是"表面成功"：引擎 `rc=0`，但 `/proc/modules` 里没有 `kernelsu`，管理器显示未安装，`su` 仍不可用，**只有 SELinux 变成 Permissive**。

原因：从应用数据目录直接 exec 被 SELinux 上下文拦住，late-load 根本没跑起来。加上 bind-mount 到系统路径后一次成功：

```
$ adb shell su -c id
uid=0(root) gid=0(root) groups=0(root) context=u:r:ksu:s0

$ adb shell su -c 'grep kernelsu /proc/modules'
kernelsu 225280 1 - Live 0x0000000000000000 (O)

$ adb shell ls -l /system/bin/su
-rwxr-xr-x 1 root root 6024848 ... /system/bin/su   ← 大小正是捆绑的 ksud
```

## 四、从"能用"到"能做成工具"：四个观测陷阱

工具化之前，先要能稳定判断"这次到底成没成"。这一段花的力气最多，因为四次得出的结论是错的。

### 陷阱 1：一次开机只能成功一次

`dfr_lkm` 加载之后，同一 boot 内再次运行会走短路分支：引擎约 1 秒返回、不打补丁、不触发、不 bind-mount。第一次运行约 2.9 秒，短路约 1 秒。

早期把这个差异当成"短路判定阈值"，结果把一次正常运行误判成短路。**结论：只有重启后的第一次运行才是有效样本。**

### 陷阱 2：payload 真的执行了，但日志是 0 字节

脚本里的重定向建出了日志文件，内容却是空的，于是"载荷没执行"这个结论写错了两次。改成只写字面量与 `$?`、不做命令替换之后，日志才开始有内容：

```
tx1-start
tx1-ksud-real-present
tx1-cp=0
tx1-chmod=0
tx1-mount=0
tx1-lateload=0
```

**结论：观测手段本身要当代码来设计。** 现在 payload 只写 `/data/local/tmp/g2sm-tx1.log`：root 可写、adb 可直接读，不需要 `run-as`。

### 陷阱 3：`su-missing` 是时序假象

日志先记录到 `tx1-su-missing`，但紧接着人工检查时 `/system/bin/su` 已经存在。原因是 `late-load` fork 出常驻进程后立刻返回，bind-mount 稍后才落地。

修法：加有界等待（最长数秒）再判定。

### 陷阱 4：应用里的日志"消失"

运行日志只存在内存里。系统弹窗（管理器提示、权限提示）导致 Activity 重建后，界面显示"没有日志"，而磁盘上记录完整。

修法：每次运行落盘一个文件，页面从磁盘回填，不依赖内存状态。同一次改版还加了构建标记与安装包 SHA-256，否则两个只改了载荷、界面完全一样的版本无法区分。

## 五、最关键的一次否证：应用根本看不到 su

拿到 su 之后，最自然的写法是应用里 `ProcessBuilder("/system/bin/su")`。实测直接否掉：

```
$ adb shell su -c id
uid=0(root) ... context=u:r:ksu:s0          ← shell 可用

$ run-as <app> ls -l /system/bin/su
/system/bin/su: No such file or directory    ← 应用不可见
```

su 的 bind-mount 位于应用不共享的 mount namespace。再加上内核侧授权门只放行 uid 2000（见 `--allow-shell`），应用这条路彻底堵死。

**结论：应用永远不碰 su，特权调用必须放在 root 侧。** 这条否证决定了后面整个结构。

---

## 六、通道选型：五个候选，四个被否

需要一个"应用 → root"的命令通道，而且不能用轮询重新提权（一次开机只有一次机会）。

| 候选 | 实测结果 |
|---|---|
| 应用直接 exec su | 应用 uid 下路径不存在，且授权门只认 uid 2000 |
| FIFO | 应用写 `app_data_file:fifo_file` 被静默拒绝（`Permission denied`，无 avc 记录）；root 建的 FIFO 又缺应用的 MLS 类别 |
| abstract socket | 应用可建，但 root 侧没有可用的 shell 客户端去连 |
| binder | 需要一个常驻且被系统认可的注册方，风险与成本都不可控 |
| **普通文件信箱** | **双向验证通过** |

文件信箱的三个结论是踩出来的，不是设计出来的：

1. root **可以**读写应用创建的文件；
2. 应用**读不了** root 创建的文件（root 建的文件只带 `s0`，不带 `s0:cXXX,cYYY`）；
3. 所以三个通道文件必须**由应用创建**：`req`（写命令）、`out.log`（助手回写）、`status`（助手的 pid 与心跳）。

```
files/tx2/req      ← 应用写：第一行序号，第二行命令
files/tx2/out.log  ← 助手追加 stdout/stderr
files/tx2/status   ← 助手写 pid；应用用 mtime 判断存活
```

心跳不是多余设计：助手被杀后 pid 会留在磁盘上，而应用无法 stat 一个 root 进程，只有 mtime 能表达"还活着"。

## 七、最终结构：两个事务

把"提权"和"发命令"拆开，是被失败逼出来的结论：

- 合成一步时，"载荷没跑起来"和"`am` 参数不对"表现完全一样，实测两种都出现过，界面都只是"没有反应"；
- 拆开之后，事务 1 的结论只有"通道就绪 / 不可用"，事务 2 的结论只有"已发送 / 失败"，日志能直接定位。

```
事务 1（Engine）
  DFBridge → IPsec 建链 → 引擎提权 → 执行 payload
  payload：落 ksud → bind-mount → late-load --allow-shell → 启动常驻助手
  应用：等待 /system/bin/su（有界）→ 等待助手心跳 → 状态 Ready / Failed

事务 2（MenuTx）
  应用：写 req（序号 + am start 命令）
  助手：读到序号变化 → su -c "<命令>" → 追加 out.log
  应用：读增量，展示摘要
```

`am` 为什么必须在 `su -c` 里跑：payload 所在的 `vendor_modprobe` 上下文里，`am` / `cmd` / `app_process` 这类 Java 进程会被 SIGKILL（退出码 137），而 `sh`、`cp`、`mount`、`echo` 正常。`/proc/self/attr/exec` 也写不进去（返回 1），无法自行换域。

## 八、一页速查

```sh
# 事务 1 之后，确认状态
adb shell ls -l /system/bin/su          # 存在 => su 已落地
adb shell su -c 'grep kernelsu /proc/modules'   # kernelsu ... Live (O)

# 助手是否在跑（应用私有目录需 root 或用应用自身查看）
adb shell su -c 'cat /data/data/<pkg>/files/tx2/status'

# payload 自己的执行轨迹
adb shell cat /data/local/tmp/g2sm-tx1.log
```

排障顺序固定为：载荷日志 → `/system/bin/su` 是否存在 → 助手心跳 → 助手输出的 `am` 结果 → 是否在同一次 boot 内重复运行过。

## 九、已知限制

| 项 | 说明 |
|---|---|
| 次数 | 一次开机只成功一次，重复运行走短路分支 |
| 生命周期 | 重启后内核模块、临时 su、SELinux 状态全部消失 |
| 依赖 | 设备仍需存在 DirtyFrag 提权链，系统更新后可能失效 |
| 架构 | 仅 arm64-v8a |
| 通道延迟 | 助手轮询信箱，约 200 ms 量级 |

---

## 十、边界

全程只写应用数据目录与 `/data/local/tmp`。不写 `/system`、`/vendor`、`/product`、`/odm`、`/system_ext`、`prism`、`optics`；不碰 `boot`、`vbmeta`、`efs`、`param`、`modem`；不关 verity；不解 BL。保修位之所以不动，是因为这套方案在机制上碰不到 e-fuse —— 而不是因为"操作很小心"。
