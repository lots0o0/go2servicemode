# 技术说明

探索过程见 [01-探索记录](01-探索记录.md)。这里只描述最终结构。

## 分层

```
UI          ui/MainScreen · LogScreen · LogViewer · AboutScreen · Glass · Components · Theme
事务层      Engine（事务 1） · MenuTx（事务 2）        两者互不引用
模型层      LogStore（落盘/回填） · RunService（前台服务）
桥层        df/root/DFBridge.java（IPsec 建链、载荷落盘、原生调用）
设备侧      assets/payload.sh（事务 1） · assets/helper.sh（事务 2 助手）
```

依赖单向向下：UI 不知道 su 存在。

## 事务 1：建立临时 su

```
MainScreen → Engine.establishSu()
  → DFBridge.establishSu()
      → IpSecManager：UDP 封装 socket、SPI、transform
      → 落盘 ksud-real / helper.sh / payload.sh 到应用数据目录
      → nativeRunAll(...)：引擎提权并执行 payload
  → 等待 /system/bin/su（有界）
  → 等待助手心跳（status 的 mtime）
  → 状态 Ready / Failed
```

payload 在 `u:r:vendor_modprobe:s0` 中执行，只做四件事：落一份 ksud、bind-mount 到 `/system/bin/atrace`、`late-load --allow-shell`、启动助手。**payload 里没有任何 `am` 调用**，也不接受运行时传入的字符串。

## 事务 2：发送命令

```
MainScreen → MenuTx.request(key)
  → 校验白名单 → 写 files/tx2/req（序号 + 命令）
助手         → 读到序号变化 → su -c "<命令>" → 追加 out.log
MenuTx      → 读增量 → 日志页展示
```

白名单只有两个值：`4238378`（GCF 菜单）、`27663368378`（NAS / 主菜单）。校验在 Kotlin 与 Java 桥各做一次。

## 为什么是这个通道

| 通道 | 结论 |
|---|---|
| 应用 exec su | 应用 uid 下路径不存在，授权门只认 uid 2000 |
| FIFO | 应用写 `app_data_file:fifo_file` 被静默拒绝；root 建的 FIFO 缺应用 MLS 类别 |
| abstract socket | root 侧无可用 shell 客户端 |
| binder | 需要常驻且被系统认可的注册方，风险不可控 |
| 文件信箱 | 双向验证通过 |

通道文件必须由应用创建。root 创建的文件只带 `s0`，不带 `s0:cXXX,cYYY`，应用随后读不了。

## 状态机

```
NotRun ──点击──▶ Running ──助手心跳正常──▶ Ready
                    └──超时/引擎失败──▶ Failed
```

事务 2 的可用性是 `Ready` 的推论，不单独维护状态。

## 日志

- 每次运行一个文件：`files/runs/run-yyyyMMdd-HHmmss.log`
- 首行 `## <摘要>`，其后是带时间戳的原始行
- 页面只列运行历史；完整内容在独立查看器里，单滚动容器、虚拟化、跟随末尾
- 启动时从最新文件回填，不依赖内存状态

## libexp.so 补丁

引擎里硬编码了上游的载荷路径，长度固定 48 字节。构建前把该字符串原地替换成本工程的路径，余下用 NUL 填充，文件大小不变。步骤可复现，见 `tools/patch_libexp_path.py`。不打补丁时，载荷会被写到上游路径，引擎执行时会找不到本工程的文件。
